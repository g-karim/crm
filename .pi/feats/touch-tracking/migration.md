## Подготовка и применение

Схема устанавливается штатным импортёром Frappe 16.25, в контексте нужного сайта/System Manager, при приостановленных записях. Новых patches в этой ветке нет. Не включать scheduler на проверочной копии:

```python
from frappe.modules.import_file import import_file_by_path
from frappe.core.doctype.scheduled_job_type.scheduled_job_type import sync_jobs

assert not frappe.db.exists("DocType", "CRM Touch Settings")
frappe.flags.in_migrate = True
try:
    for name in (
        "crm_touch_settings", "crm_touch_policy", "crm_touch_event",
        "crm_touch_change", "crm_touch_receipt", "crm_lead", "crm_deal",
    ):
        path = frappe.get_app_path("crm", "fcrm", "doctype", name, name + ".json")
        assert import_file_by_path(path, force=True, reset_permissions=False)
    assert not frappe.get_doc("CRM Touch Settings").enabled
    sync_jobs()
    frappe.db.commit()
    frappe.clear_cache()
finally:
    frappe.flags.in_migrate = False
```

DDL не является полностью откатываемой транзакцией: до импорта нужна проверенная полная копия. Повторять этот шаг на уже мигрированном сайте нельзя без проверки его состояния. Функциональный откат сохраняет дополнительную схему. Штатный `sync_jobs()` при возврате старого кода может добавить audit-комментарии об удалении двух заданий tracking; исходные пользовательские комментарии не меняются.

Из контекста правильного сайта/System Manager:

```python
from crm.touch_tracking_migration import prepare, apply

manifest = prepare()
# Сохранить полный manifest отдельным файлом с chmod 600, до изменения БД.
# Не публиковать его в Git/логах: в нём есть пользовательские представления.
result = apply(manifest)
frappe.db.commit()
```

`prepare()` читает ID, создание, modified, текущий статус, прежнюю дату лидов, новую дату, штатную цепочку статусов, настройки и представления. Manifest привязан к сайту и проверяется по SHA-256. В нём сохранены исходные значения для отката; идентификатор нельзя брать с тестового сайта.

`apply()` блокирует текущие строки карточек, истории и представлений и сверяет их с manifest. Изменённые источники требуют нового `prepare()`. Проверяется именно текущая версия заблокированных строк, включая случай ранее открытого снимка транзакции.

- Lead: точная прежняя дата `custom_crm_status_sort_date`, если она валидна. При отсутствии — создание и достоверная штатная история.
- Deal: максимум создания и времени новых строк достоверных переходов штатной цепочки. Последняя открытая строка с пустым `to` учитывается. Произвольный modified не используется.
- Более новая существующая дата касания не уменьшается. Нет исторических фиктивных событий и пересохранения бизнес-документов.
- Только ключи прежнего поля в сохранённых Lead-представлениях переименовываются. Направления сортировки, значения фильтров, ручной порядок Kanban и прочие настройки сохраняются.
- Начальный профиль: создание и реальная смена статуса для Lead/Deal. Поля, задачи, комментарии, письма, мессенджеры, телефония и разрешения автоматизации выключены.
- Старый writer прекращает обновления. Обычное выключение нового tracking не запускает его повторно.
- Повтор с тем же активным ID ничего не пересчитывает и не меняет новые данные, настройки или представления.

При ошибке откатить транзакцию. Обычная ошибка валидации также отменяет частичные записи внутренним savepoint. Deadlock, конфликт SQL-снимка и потеря соединения передаются вызывающей стороне: нельзя объявлять миграцию успешной или повторять только её часть. Для `apply` после полного rollback подготовить свежий manifest; для `rollback` использовать исходный manifest и новую транзакцию. Бизнес-запись не воспроизводится.

После commit проверить полный порядок лидов, начальные даты сделок, права, обычные записи сотрудника и поиск по телефону. Проверить обслуживание Pending-событий. Возобновить записи сайта.

## Функциональный откат

Сначала остановить запуск новых событий и обработать ранее принятые Pending-события. В контексте исходного сайта, пока новый код доступен:

```python
from crm.touch_tracking_migration import rollback

result = rollback(manifest)
frappe.db.commit()
```

Откат выключает tracking и возвращает прежний writer. Старые даты лидов восстанавливаются из сохранённого значения плюс **реальные переходы статуса после cutover**, включая новые лиды. Новое поле может содержать другие взаимодействия, поэтому копировать его обратно целиком нельзя.

Новые карточки, задачи, комментарии, связи, creation, modified, новые даты касания и журналы сохраняются. В представлениях восстанавливаются только слоты, всё ещё равные значению миграции; последующие выборы пользователя сохраняются. Повторный rollback ничего не меняет.

## Возврат прежнего кода

Функциональный откат с текущим кодом — достаточный первый способ выключить функцию. Если нужен прежний код:

1. Завершить функциональный откат и проверку сохранённых данных. Остановить только задания касаний/Novofon producer и дождаться их уже запущенных задач. Не удалять очередь бизнес-операций.
2. Вернуть совместимые версии CRM, fcrm_telephony и прежние frontend-артефакты. Обновить процессы и очистить cache/hooks сайта.
3. **Сохранить добавленную схему**: last_touch_at, Singleton и журналы остаются в БД и метаданных. Не запускать migrate на старом checkout и не удалять поля/DocType. Иначе можно сломать сохранённые пользователем колонки или потерять возможность повторного включения.
4. Синхронизировать штатное расписание с hooks возвращённого кода:

   ```python
   from frappe.core.doctype.scheduled_job_type.scheduled_job_type import sync_jobs
   sync_jobs()
   frappe.db.commit()
   ```

   Проверить отсутствие активных заданий, указывающих на отсутствующие модули tracking/Novofon producer. У остальных приложений остаётся штатное расписание.

5. Проверить прежнюю сортировку, создание и смену статуса, поиск, пользовательские представления. Журналы касаний сохраняются для последующего возврата нового кода.

Stage 6 проверил этот путь на исходных CRM/fcrm HEAD с сохранённой дополнительной схемой и target-кодом Frappe 16.25. Полный rollback production-процессов, полная копия/восстановление и живые каналы остаются проверками выпуска.

## Границы проверки Stage 6

Отдельная БД и сайт `crm-touch-stage6.localhost`, source Frappe 16.25 по production SHA, MariaDB 11.8.8, Python 3.14.6; fixture schema взята из пустого локального test bench. Источники messenger/fcrm сверены с production. На реальной MariaDB 10.6 read-only проверены используемые базовые выражения дат; полный restore на 10.6 в Stage 6 не выполнялся.

Репетиция использует исходные ID/даты 3 806 лидов, 3 сделок, 4 507 строк статусов и 28 представлений. Полные бизнес-значения и файлы не восстанавливались. Проверены точный порядок всех лидов, отсутствие изменения остальных столбцов/связей/прав/истории на fixture DB, три мигрированных представления, повтор, новые нативные записи, откат и прежний код. Все временные business fixtures удалены только из проверочной БД.

Novofon на проверенном production-сайте выключен, ключи не настроены; шесть почтовых аккаунтов имеют выключенный приём/отправку, messenger channels отсутствуют. Пользователь сообщил, что используется Novofon; его живой аккаунт и полные PBX-сценарии ещё нужно проверить. Allowlist адаптеров не включается этой миграцией.


## Выпуск Stage 7 на MariaDB 10.6

Выпуск 2026-10-09 использовал полный dump/файлы/ключ и изолированную копию на MariaDB 10.6.23 / Python 3.14.4 / точном Frappe 16.25.0. На этой копии проверены новый код, узкая синхронизация схемы, нативные карточки/статусы/комментарии/сроки задач, поиск телефона, откат функции и возврат старого кода с добавленной схемой. Обычные DocPerm и Custom DocPerm независимо сверены с исходным dump.

Перед cutover Таткардан был переведён в maintenance/pause, штатные shared workers и scheduler завершены плавно; очереди не очищались. После свежей полной копии выполнены snapshot, узкий импорт, prepare/apply, проверка всех защищённых бизнес-строк/прав и точного порядка 3807 лидов, затем перезапуск web/workers и восстановление исходных флагов сайта. Схема и профиль включены только на Таткардане; проверены list API остальных десяти CRM-сайтов и неизменность их конфигураций.

Стандартный Lead list Усмана (CRM View Settings 18) отдельно переключён с `modified desc` на `last_touch_at desc, creation desc, name desc` по прямому разрешению пользователя. Миграция сама сохраняет явные пользовательские сортировки. Для этого отдельного переключения сохранён override manifest; при откате возвращать его прежний order только если сотрудник не выбрал более новую сортировку. Остальные slots и представления сохранены.

Новый frontend собран заранее и проверен в реальном браузере на полной копии (Administrator и существующий Sales User). Production Frappe не содержит `apps/frappe/ui`, поэтому выпуск использовал проверенный артефакт с сохранёнными SHA-256, wrapper и снимком UI build input; framework не обновлялся. Старые frontend-артефакты и hashed chunks сохранены. Старое поле даты не удалено: только новый writer активен, очистка остаётся после подтверждения стабильности.

Финальная предрелизная копия также повторно полностью восстановлена в отдельную БД/site: все 19 защищённых наборов совпали с cutover snapshot, 11 локальных файлов проверены, ключ шифрования сохранён. Единственный remote File — внешняя аватарка secure.gravatar.com; это не файл собственного object storage. Копия БД/public/private/config и manifests сохранены вне сервера с доступом только владельцу. Они не предназначены для Git/PR.


### Проверка прав и выдачи frontend

После копирования из private staging каталога явно выставить `0755` каталогам и `0644` обычным файлам **только** в `apps/crm/crm/public/frontend`. `copytree` переносит mode исходных каталогов: в Stage 7 private `0700` первоначально привёл к 404 от Nginx, хотя Frappe-процесс копии читал файлы и браузерные тесты проходили. Права исправлены; 26 entry/preload JavaScript/CSS URL возвращают HTTP 200 с корректным content type через HTTPS origin/Nginx. Не менять права public/private пользовательских файлов или каталогов backup. Проверять статические URL через фактический Nginx до завершения maintenance, включая lazy chunks; наличие файла и native backend API не подтверждают его доступность браузеру.
